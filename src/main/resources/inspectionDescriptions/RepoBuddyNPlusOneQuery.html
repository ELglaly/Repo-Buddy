Detects the classic N+1 query pattern, where a list of N entities causes N + 1 queries. Two shapes are reported: 
for (User user : users) {
    user.getAddresses().size();        // (1) lazy @OneToMany loaded once per user
    authorRepository.findById(user.getAuthorId());  // (2) one query per iteration
}
  1. Lazy association in a loop – accessing a lazily-loaded JPA association on a for-each (or stream-iteration) loop variable, or on a per-iteration element access in an indexed loop (list.get(i), iterator.next(), array[i]).
  2. Query call in a loop – calling a Spring Data repository method, a JPA EntityManager/Query read, a Hibernate Session read, or a JdbcTemplate query inside any loop (for/for-each/while/do-while) or a stream-iteration lambda / method reference. The query that drives the loop itself (e.g. for (X x : repo.findAll())) is not flagged.

The inspection is intentionally conservative to avoid false positives. It fires only when:

  • the receiver's type is an @Entity, and
  • the accessed property is a clearly lazy association — @OneToMany/@ManyToMany (lazy by default), or @ManyToOne/@OneToOne declared with fetch = FetchType.LAZY.

Associations annotated with a sufficiently large Hibernate @BatchSize are ignored (configurable threshold). Safe accesses such as getId() are never reported.

No automated fix is offered because the correct remedy lives in the query that loads the data — add a JOIN FETCH or an @EntityGraph, or batch the per-iteration lookups into a single findAllById(ids) call before the loop. Query-in-loop detection can be turned off in the inspection options.

By default RepoBuddy runs in panel-only mode: these findings appear in the RepoBuddy Issues tab, the editor banner, and the status-bar counter rather than inline. Disable panel-only mode under Settings | Tools | RepoBuddy to see them as ordinary editor warnings.
